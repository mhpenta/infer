# int8 weights

`ops.PackInt8` quantizes a linear weight to int8, and
`llama.LoadWith(dir, llama.Options{Int8: true})` loads a decoder that way. This
note covers the format, how it is tested, what it measured, and why it falls
short of the 2× decode speedup the bandwidth arithmetic promised, on Apple
silicon at least.

## Format

Symmetric, one scale per output column: row j of a weight (output j of the
product) is stored as integers q in [-127, 127] with scale `max|w[j]| / 127`,
rounded to nearest, so every weight is within half a scale step. Panels keep
the float32 layout (16 columns, k-major) with one byte per value.

The kernels widen q to float32 in registers and sum exactly as for float32
panels. Each output is then scaled once, and the bias added, in Go, after a
block's last kc slice (`scaleColumns`). Scaling outside the kernels leaves
every assembly epilogue unchanged. It also gives a bit-exact definition: an
int8 product equals the float32 product on the integers, followed by
`float32(sum·scale) + bias`.

In `model/llama`, `Options.Int8` quantizes every linear layer and the output
layer. The token embeddings stay bf16: generation reads one row of them per
token. Keeping the output layer in bf16 made no measurable difference to
quality, so it is quantized too.

| | MiniCPM5-1B | MiniCPM5-2B |
|---|---|---|
| bf16 weights in memory | 2.2 GB | 5.0 GB |
| int8 weights in memory | 1.3 GB | 2.8 GB |
| read per generated token, bf16 | 1.8 GB | 4.5 GB |
| read per generated token, int8 | 0.9 GB | 2.2 GB |

## Kernels

| Architecture | Widening | Kernels |
|---|---|---|
| amd64 (AVX2, AVX-512) | `VPMOVSXBD` (load and sign-extend 8 or 16 bytes), `VCVTDQ2PS` | 6×16, 12×32 and one-row, generated by `scripts/gen_amd64_kernels.py` like the bf16 ones |
| arm64 (NEON), 6×16 | `SXTL`, `SXTL2` twice, `SCVTF` | `kernel_int8_arm64.s` |
| arm64 (NEON), one row | flip each byte's sign bit (u = q + 128), `TBL` the bytes into lanes of `u, 0x00, 0x00, 0x4B` (the float 2^23 + u), subtract 2^23 + 128 | `kernel_int8_arm64.s` |
| portable Go | `float32(q)` | `kernel_go.go` |

Go's arm64 assembler lacks `SXTL`, vector `SCVTF` and vector `FSUB`, so those
are `WORD` macros whose encodings were checked against clang.

## Tests

- `ops`: int8 products are bit-identical to the float32 product on the
  integers, then scaled. This covers the 6×16, 12×32 and one-row kernels,
  with and without bias, over shapes around the panel and kc edges. A
  swapped column group in either NEON kernel fails it. The one-row path also
  joins the gemv-equals-gemm exactness test. The quantizer's error bound,
  ±127 range and zero rows are tested, and AVX-512's startup self-check
  includes int8.
- `model/llama`: `TestInt8MatchesBF16` compares int8 MiniCPM5-1B with bf16
  (which matches PyTorch) on every golden sequence, teacher-forced:

| Case | Positions | Top-1 agrees | Mean KL(bf16 ‖ int8) | Perplexity, bf16 → int8 |
|---|---|---|---|---|
| 0, raw text | 13 | 100% | 0.0014 nats | 4.57 → 4.48 |
| 1, chat | 34 | 94.1% | 0.0072 | 185.5 → 195.1 |
| 2, chat | 98 | 95.9% | 0.0037 | 45.2 → 46.6 |
| 3, 2,461-token chat | 2,484 | 99.9% | 0.0003 | 1.206 → 1.207 |

  Greedy generation gives PyTorch's tokens on all four cases. The test
  requires ≥ 90% top-1 agreement, a mean KL ≤ 0.02 nats and identical greedy
  tokens.

- **Caveat: long reasoning traces diverge.** On MiniCPM5-2B with thinking
  on, "A company's revenue grew from $80B to $94.9B. What is the growth rate?
  Be brief." gets a clean 213-token answer in bf16. The int8 model picks a
  different fifth token, reaches 18.6% too, and then loops on "Or 18.6%
  growth. Or 18.6% increase." up to the token limit. Under greedy decoding,
  one changed token changes everything after it. Loops like this are what
  sampling and repetition penalties exist for, and infer has neither yet. So
  the golden-case agreement above says the distributions are close; it does
  not promise the same long answers.

## Speed (M2 Max, 12 threads)

Each figure is the best of several interleaved runs on a mostly idle machine
(load average about 6). A first pass under heavy load (15–19, with 40 GB of
swap) gave the same ratios.

| One row, all threads | bf16 | int8 |
|---|---|---|
| 12,288 × 2,048 (2B gate + up) | 0.55 ms (92 GB/s) | 0.43 ms (59 GB/s) |
| 2,048 × 6,144 (2B down) | 0.21 ms (121 GB/s) | 0.26 ms (48 GB/s) |

| Generation | bf16 | int8 |
|---|---|---|
| MiniCPM5-1B decode | 37.4 tokens/s | 42.2 tokens/s (1.13×) |
| MiniCPM5-1B, 65-token prompt | 323 ms | 363 ms |
| MiniCPM5-2B decode | 15.3 tokens/s | 17.5 tokens/s (1.14×) |
| MiniCPM5-2B, 65-token prompt | 873 ms | 990 ms |

**On NEON, the int8 kernels are limited by instructions, not memory.** The
one-row int8 kernel streams 48–56 GB/s where bf16 reaches 86–115. bf16
widens 16 values with 4 zips. int8 needs 4 table lookups, 4 subtractions and
a sign flip, or 6 sign-extends and 4 conversions. Removing the subtractions
and the flip (giving wrong results) still left int8 at 63–71 GB/s, so no
reshuffle of weight-only int8 widening closes the gap. Prompts are slower
too: the 6×16 kernel spends 10 instructions widening each panel row against
bf16's 4.

**On amd64 it should be different.** There, int8 widening is a sign-extending
load plus one conversion, the same instruction count as bf16's
zero-extending load plus shift, for half the bytes. So it should approach the
bandwidth ratio. This is not measured: Rosetta has no meaningful AVX timing,
so it needs a real x86 host.

## Next: int8 activations with integer dot products

The fast path on ARM, and the one llama.cpp uses for its Q8_0 format,
quantizes the activations too. Each one-row product would then use `SDOT`,
16 int8 multiply-adds per instruction, against 4 for `FMLA`, with no
widening at all. That would make decoding bandwidth-bound again.

It changes three things:
- **Panel layout:** each 32-bit lane holds 4 consecutive k values of one column.
- **Numerics:** the activation vector is quantized per block, which adds
  error beyond the weights, to be measured like the table above.
- **amd64 kernels:** AVX-512 VNNI (`VPDPBUSD`), or AVX2's `VPMADDUBSW` with
  sign tricks.
